# SCOT Upgrade Notes

## 4.7.2

### Meilisearch credential separation

Meilisearch now reads its master key from a dedicated
`scot4-meilisearch-secrets` Secret. The running SCOT API receives a separately
scoped key that is generated by Meilisearch during API pod initialization.

Helm creates this Secret on a new installation and retains it across upgrades
and uninstalls. During the first upgrade of an existing installation, the
template copies the current `MEILI_MASTER_KEY` from `scot4-env-secrets`. It only
generates a new key when neither the dedicated nor legacy Secret contains one.
This avoids changing the key protecting an existing Meilisearch PVC.

Run the normal Helm upgrade. Each API pod waits for Meilisearch, creates or
retrieves the stable least-privilege API key, and keeps that key in a
memory-backed pod volume. The search rebuild Job uses the master key because
rebuilding requires index and settings administration.

Only after the upgrade succeeds, remove the legacy keys from
`scot4-env-secrets`:

```bash
./inst_func/inst_cleanup_legacy_meilisearch_secrets.sh
```

The supplied deployment scripts run this cleanup automatically after Helm has
updated Meilisearch to use the dedicated Secret. Set
`scot4.search.createMasterKeySecret=false` only when the Secret named by
`meilisearch.auth.existingMasterKeySecret` is managed outside this chart.

Secret preservation relies on Helm's live-cluster `lookup`, so apply this chart
with `helm install` or `helm upgrade`; an offline `helm template` render cannot
read and preserve the existing value.

### Flair Mojolicious signing secret

Existing installations created before 4.7.2 do not have
`S4FLAIR_MOJO_SECRETS` in `scot4-flair-secrets`. The supplied deployment scripts
add a securely generated value before running Helm and preserve an existing
non-placeholder value. If you run Helm manually, perform the backfill first:

```bash
./inst_func/inst_backfill_flair_mojo_secret.sh
helm upgrade # include the arguments appropriate for your deployment
```

The Helm upgrade restarts the Flair workloads so they consume the value. Users
with existing Flair sessions may need to sign in again after this first upgrade.

### Database root credential isolation

The internal SCOT and Flair databases now read their root passwords from the
dedicated `scot4-database-root-secrets` and
`scot4-flair-database-root-secrets` Secrets. On the first upgrade, Helm copies
the existing values from `scot4-env-secrets` and `scot4-flair-secrets`. New
installations generate and retain the dedicated Secrets automatically.

The supplied deployment scripts remove the legacy `ROOT_DB_PASSWORD` fields
from the application Secrets after Helm has updated the database deployments.
The same cleanup also removes the obsolete `FLAIR_DB_PASSWORD` copy from
`scot4-env-secrets`, but only after confirming that `scot4-flair-secrets`
contains the working Flair database password. After a manual Helm upgrade, run:

```bash
./inst_func/inst_cleanup_legacy_database_root_secrets.sh
```

Omitting `MYSQL_ROOT_HOST` prevents new database volumes from creating a remote
`root@'%'` account. MySQL initialization environment variables do not modify
accounts already stored on a retained volume. For an existing internal SCOT
database, inspect and remove that account locally from the database pod:

```bash
kubectl -n scot4 exec deployment/scot4-db -- sh -c \
  'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql --protocol=socket --socket=/var/lib/mysql/mysql.sock --user=root --execute="SELECT User, Host FROM mysql.user WHERE User = '\''root'\'';"'

kubectl -n scot4 exec deployment/scot4-db -- sh -c \
  'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql --protocol=socket --socket=/var/lib/mysql/mysql.sock --user=root --execute="DROP USER IF EXISTS '\''root'\''@'\''%'\'';"'
```

Use the same commands with `deployment/scot4-flair-db` for a retained Flair
database. Confirm that `root@localhost` exists before removing `root@'%'`.

### K3s API firewall exposure

New installations no longer open the K3s API port, TCP 6443, to all network
sources. SCOT supports a single-node cluster administered locally, so its
kubeconfig can reach the API over the loopback interface without an inbound
firewall rule.

An unrestricted rule created by an older installer remains in the host's
persistent firewall configuration until it is removed. Before removing it,
confirm that the kubeconfig uses a loopback API endpoint and that no remote
Kubernetes clients or additional K3s agent nodes depend on this host:

```bash
kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}'
```

For an active firewalld installation, inspect and remove the rule with:

```bash
sudo firewall-cmd --permanent --query-port=6443/tcp
sudo firewall-cmd --permanent --remove-port=6443/tcp
sudo firewall-cmd --reload
```

For an active UFW installation, inspect and remove the rule with:

```bash
sudo ufw status
sudo ufw --force delete allow 6443/tcp
```

If remote Kubernetes administration is desired, allow TCP 6443 only from
the required management network rather than reopening it to every source.
